# E2EESA 1.0 Release Guide

## Current state

Development is allowed to continue while independent review is pending.

The repository is currently at:

- candidate: **0.9.0-rc.1**
- candidate tree digest: `sha256:9d546433dde60d3157e2adb3d9c630dbc36fd92c551083f5f5189491370ce2a2`
- candidate files: **645**
- 1.0 engineering status: **ready except independent review**
- external gate: **independent expert review pending**

The pending review is a release gate, not a development freeze.

## What remains externally blocked

Only the final claim that E2EESA is ready to become 1.0 is blocked on external evidence.

The required review package is defined under `review/`.

Run:

`python review/validate_review.py --require-complete`

That command must pass before final 1.0 promotion.

## What development can continue now

Before review completion, maintainers may continue to:

- improve release tooling;
- improve reviewer handoff documentation;
- add non-candidate release automation outside the frozen candidate surface;
- prepare migration/version-promotion tooling;
- prepare final release notes;
- prepare final provenance/manifest formats;
- prepare downstream integration instructions;
- fix non-candidate tooling bugs;
- prepare scripts that are gated on review completion.

Do not silently modify the frozen 0.9 candidate and continue to call it the same reviewed candidate. Changes to frozen candidate files must be treated as review-fix changes and recorded in PR 49.

## Required review outcome

Before final promotion:

- at least three independent reviewers;
- at least two independent reviewer organizations;
- all five required review domains;
- independent cryptography/protocol review;
- all blocker/critical/high findings fixed and reviewer-accepted;
- all medium findings dispositioned and reviewer-accepted;
- final review summary content-addressed;
- live package status `ready-for-1.0`;
- `python review/validate_review.py --require-complete` passes.

## Version promotion

The 0.9 candidate intentionally preserves the internal standard basis `0.1.0-dev`.

After review completion, the promotion tool replaces the exact active literal `0.1.0-dev` with `1.0.0` across the active, non-historical specification/code/test/configuration surface. Historical 0.9 candidate and review records are explicitly excluded.

It does not automatically change:

- `profile_version`;
- `registry_version`;
- `schema_version`;
- algorithm identifiers;
- profile identifiers;
- finding IDs;
- review digests;
- historical 0.9 candidate records.

This keeps the 1.0 release version distinct from independently versioned profiles, registries, and schemas.

## Final promotion sequence

1. Independent reviewers assess the frozen 0.9.0-rc.1 candidate and submit findings.
2. Apply accepted PR 49 fixes without rewriting the historical rc.1 manifest.
3. Run `python review/validate_post_fix_tree.py` after review-driven frozen-file changes.
4. Run `python review/final_review_tree.py` to compute the exact fixed-tree digest.
5. Obtain each reviewer's final acceptance of that same fixed-tree digest.
6. Complete the combined review package and pass `python review/validate_review.py --require-complete`.
7. Run `python release/validate_1_0_readiness.py --engineering-only`.
8. Run `python release/promote_to_1_0.py` to inspect the exact planned version changes.
9. Run `python release/promote_to_1_0.py --apply` only after the review gate passes.
10. Run strict `python release/validate_1_0_readiness.py`, repository validation, final-release validation, unit tests, and seeded adversarial checks.
11. Tag/release `1.0.0` only after all gates pass.

## Placeholder rule

> E2EESA 1.0 engineering is complete except for independent expert review. The current validated candidate is 0.9.0-rc.1. Final 1.0 publication remains gated on independent cryptography/security review and disposition of its findings.
