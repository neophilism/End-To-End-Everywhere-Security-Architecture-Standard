# Observatory Data Architecture

**Status:** Normative. **Version:** 0.1.0. **Milestone:** PR 35.

The Observatory data architecture separates the canonical evidence store from query-optimized projections.

The canonical logical model is relational and append-only.

Graph and search stores are derived projections. They MAY be rebuilt, replaced, or dropped without changing evidence identity.

## 1. Authority boundary

The authoritative state consists of:

- PR 34 evidence bundle bytes;
- the bundle/manifest digests;
- canonical relational rows derived from that bundle; and
- immutable source content addressed by entity digest.

A graph database, RDF store, search engine, vector index or cache MUST NOT become the only copy of evidence required to reconstruct provenance.

A projection MUST identify the exact source bundle digest and projection version.

## 2. Canonical relational model

The logical relational model contains:

- `evidence_bundles`;
- `content_objects`;
- `agents`;
- `entities`;
- `activities`;
- `activity_acquisitions`;
- `activity_agents`;
- `activity_used_entities`;
- `activity_generated_entities`;
- `events`;
- `event_subjects`;
- `event_attributes`;
- `citations`;
- `event_citations`;
- `integrity_anchors`; and
- `anchor_verification`.

Rows scoped to a bundle use the bundle digest plus the local PR 34 identifier as their stable relational identity.

## 3. Raw content storage

Large source bytes need not be stored inside the relational database.

The relational `content_objects` table stores the content SHA-256 digest and known byte length. Media type, content-addressed/object-store URI, source URI and source-native identity remain bundle-scoped entity metadata because identical bytes can appear in more than one evidence context.

Any external blob/object store is an implementation choice.

Object-store paths MUST NOT be treated as identity. The content digest is identity.

## 4. Append-only semantics

Canonical evidence tables are append-only.

Corrections create:

- a new entity;
- a new evidence bundle revision; or
- both.

They do not update the bytes/digest relationship of a prior canonical record.

Reference PostgreSQL DDL includes mutation-denial triggers for canonical evidence tables. Deployments MAY enforce append-only behavior through equivalent database permissions, immutable storage, database policy, or hardware-backed controls.

## 5. Transaction boundary

Ingestion of one evidence bundle MUST be atomic with respect to the canonical relational store.

Either:

1. the complete bundle and all canonical rows are committed; or
2. no canonical rows for that bundle are visible.

Projection updates are not part of the canonical commit and MAY occur asynchronously.

## 6. Projection checkpoint

Each derived projection stores or exposes a checkpoint containing:

- source bundle digest;
- projection type;
- projection version;
- projection digest;
- generated-at time; and
- source relational row-set digest.

A consumer MUST be able to determine which canonical evidence revision produced a projection.

The projection-manifest digest covers the source bundle, relational row-set digest, row counts and projection digests/counts. It intentionally excludes `generated_at`, so rebuilding identical logical projections at a later time produces the same logical manifest digest while retaining a new generation timestamp.

## 7. Property graph projection

The property-graph projection is optimized for traversal.

Node types:

- Bundle;
- Agent;
- Entity;
- Activity;
- Event;
- Citation;
- IntegrityAnchor.

Edge types include:

- `CONTAINS`;
- `PREVIOUS_BUNDLE`;
- `USED`;
- `WAS_GENERATED_BY`;
- `WAS_ASSOCIATED_WITH`;
- `WAS_DERIVED_FROM`;
- `CITES`;
- `CITATION_SOURCE`;
- `HAS_SUBJECT`; and
- `ANCHORS`.

Every projected node and edge is derived from canonical PR 34 fields.

## 8. W3C PROV RDF projection

E2EESA also supports a standards-oriented RDF triple projection.

PR 34 provenance relations map to W3C PROV IRIs:

- used → `prov:used`;
- was generated by → `prov:wasGeneratedBy`;
- was associated with → `prov:wasAssociatedWith`;
- revision/derivation → `prov:wasDerivedFrom`.

E2EESA event/citation relations use the E2EESA namespace.

The canonical output of the reference projection is an ordered array of subject/predicate/object triples. RDF serialization format (N-Triples, Turtle, JSON-LD, RDF database API) is an implementation choice.

## 9. Search projection

The search projection is document-oriented.

Search documents are generated for:

- entities;
- events;
- citations; and
- agents.

Each document contains:

- deterministic document ID;
- source bundle digest;
- projection version;
- record type;
- source/local ID;
- display title;
- normalized searchable text derived from PR 34 metadata;
- facets as name/value pairs; and
- immutable content/evidence digests where relevant.

The search projection does not fabricate full-text content that is absent from the evidence bundle. If extracted source text is required, that text must first exist as a content-addressed PR 34 derived entity.

## 10. Projection consistency

Projection validation compares a supplied projection with deterministic output regenerated from the canonical bundle.

Validation fails on:

- missing or extra relational rows;
- altered row values;
- graph node/edge omission or addition;
- RDF triple omission or addition;
- search document omission or addition;
- incorrect source bundle digest;
- wrong projection version; or
- projection-manifest digest mismatch.

## 11. Projection rebuilds

A projection implementation MAY be destroyed and rebuilt from canonical relational evidence at any time.

Rebuilding from identical canonical input and the same projection version MUST produce the same logical projection digest.

A change in projection semantics requires a new projection version.

## 12. Database choice

The logical relational model is normative; a particular RDBMS is not.

The repository includes PostgreSQL reference DDL because it provides concrete foreign keys, transactions and mutation-denial controls.

Implementations MAY use another relational database when they preserve equivalent:

- keys;
- constraints;
- append-only behavior;
- transaction semantics; and
- canonical row values.

## 13. Search and graph engine choice

No graph or search vendor is normative.

Property-graph and RDF projections are data contracts, not requirements to deploy Neo4j, Neptune, JanusGraph, a triplestore, Elasticsearch, OpenSearch or any other specific product.

## 14. Fail-closed rules

A projection MUST NOT be presented as current when:

- its source bundle is unknown;
- its source row-set digest differs;
- its projection digest fails recomputation; or
- a newer canonical bundle revision exists and the application claims “latest” semantics.

Staleness may be acceptable for explicitly historical/as-of queries, but it must be visible.
