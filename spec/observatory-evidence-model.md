# Observatory Evidence Model

**Status:** Normative. **Version:** 0.1.0. **Milestone:** PR 34.

The Observatory evidence model preserves what was observed, where it came from, how it was acquired or transformed, who/what performed those activities, how later revisions relate to earlier snapshots, and which immutable source locations support an event or assertion.

The model uses W3C PROV concepts — entities, activities and agents — without requiring a particular graph database or RDF implementation.

## 1. Immutability model

Evidence is append-only.

A source or derived entity is identified by:

- an E2EESA entity ID; and
- the SHA-256 digest of the exact content bytes represented by that entity.

Changing bytes creates a new entity. Changing an evidence bundle creates a new bundle revision.

An existing entity or bundle MUST NOT be rewritten in place while retaining the same digest or revision identity.

## 2. Bundle identity

Every evidence bundle contains:

- bundle ID;
- revision;
- previous bundle digest for revisions after 1;
- creation time;
- agents;
- entities;
- provenance activities;
- observed events;
- citations;
- immutable manifest digest;
- integrity anchors; and
- final bundle digest.

The **manifest digest** covers the evidence core but excludes integrity anchors so that external proofs can anchor a stable digest.

The **bundle digest** additionally covers the manifest digest and integrity-anchor metadata, while excluding only the bundle-digest field itself.

## 3. Canonical representation

E2EESA 0.1 evidence records use a deterministic JSON subset:

- fixed ASCII schema keys;
- no floating-point values;
- no duplicate object keys;
- UTF-8;
- lexically sorted object keys;
- no insignificant whitespace; and
- strings preserved exactly without Unicode normalization.

This is designed to remain compatible with RFC 8785/JCS requirements for the constrained evidence schema. Implementations claiming general RFC 8785 support MUST use or test against a conforming JCS implementation rather than assuming arbitrary JSON serialization is equivalent.

## 4. Agents

An agent is responsible for or participates in provenance activities.

Agent types are:

- `person`;
- `organization`;
- `software`; and
- `service`.

Each agent records:

- agent ID;
- type;
- name;
- version when applicable; and
- identity/reference URI when available.

A software acquisition tool SHOULD record its exact version.

## 5. Entities

Entity types are:

- `source-snapshot`;
- `dataset`;
- `artifact`;
- `derived-record`;
- `report`; and
- `other`.

Each entity records:

- entity ID;
- entity type;
- SHA-256 content digest;
- media type;
- byte length when known;
- immutable or retrieval URI when available;
- original source URI when applicable;
- source-native identifier when applicable;
- acquisition time when applicable; and
- `revision_of` when the entity supersedes an earlier entity.

A revision is a new entity. `revision_of` MUST be acyclic.

A source snapshot with a source URI MUST be generated by an `acquire` activity.

## 6. Activities

Activities describe provenance operations, not real-world events.

Activity types are:

- `acquire`;
- `extract`;
- `transform`;
- `normalize`;
- `classify`;
- `review`; and
- `publish`.

Each activity records:

- activity ID;
- type;
- start/end time;
- participating agent IDs;
- entities used;
- entities generated;
- method/reference identifier; and
- digest of parameters/configuration when material.

An activity end MUST NOT precede its start.

A non-acquisition activity that generates a derived entity MUST use at least one prior entity.

### Acquisition metadata

An `acquire` activity additionally records:

- transport/method;
- source URI;
- retrieval time;
- response status when applicable;
- ETag when present;
- Last-Modified value when present;
- digest of material response headers when retained; and
- request/reference identifier when retained.

The acquisition record does not substitute for hashing the retrieved content.

## 7. Real-world events

A provenance activity such as “downloaded a filing” is distinct from a real-world event such as “policy published” or “vulnerability added to a catalog.”

Event records contain:

- event ID;
- event type;
- occurrence start;
- optional occurrence end;
- subject IDs referencing entities or agents;
- one or more citation IDs; and
- optional structured attributes as name/value records.

Every event MUST have at least one citation.

An event time is a claim supported by its citations; it is not inferred from acquisition time unless the source explicitly supports that equivalence.

## 8. Citations

A citation always points to an immutable evidence entity, never merely to a mutable live URL.

Each citation records:

- citation ID;
- entity ID;
- locator kind;
- locator value;
- optional digest of quoted/extracted bytes; and
- optional note.

Locator kinds are:

- `page`;
- `line-range`;
- `section`;
- `fragment`;
- `timestamp`;
- `record`; and
- `other`.

If a live URL is useful to a human reader, it belongs on the source entity; the citation still binds the immutable snapshot entity.

## 9. Bundle revisions

Revision 1 has no previous bundle digest.

Every later revision MUST identify the SHA-256 bundle digest of its immediate predecessor.

The revision number MUST increase by one in a verified revision chain.

PR 34 validates the local revision pointer. PR 35 storage architecture defines efficient persistence and graph traversal of complete revision chains.

## 10. Integrity anchors

Content hashing establishes identity, not authorship or proof-of-time.

E2EESA therefore supports multiple complementary integrity anchors:

### Detached signature

Records a detached signature proof over either the manifest digest or an entity content digest.

Cryptographic verification is delegated to an external standards-compliant verifier. PR 34 does not implement a new signature scheme.

### RFC 3161 timestamp

Records an RFC 3161 time-stamp token proof over the manifest or entity digest.

The evidence model records the TSA/provider, proof digest, proof reference, asserted time, and external verification result.

### Transparency log

Records a transparency-log inclusion/checkpoint proof over the manifest or entity digest.

The model records log identity, entry/checkpoint reference, proof digest, and external verification result.

These anchors are complementary and MAY coexist.

## 11. Anchor verification

An integrity anchor may be:

- `unverified`; or
- `verified`.

A `verified` anchor MUST record:

- verifier identity;
- verifier version;
- verification time; and
- verification-result digest/reference.

PR 34 validates evidence about verification; it does not itself verify RFC 3161 tokens, signatures, or transparency proofs.

## 12. Provenance consistency

Validation MUST fail when:

- IDs are duplicated;
- an activity references unknown agents/entities;
- a citation references an unknown entity;
- an event references an unknown subject or citation;
- a revision pointer references an unknown entity or forms a cycle;
- a source snapshot with source URI lacks an acquisition activity;
- a derived entity is generated without source inputs;
- an entity is generated by conflicting activities;
- activity/event time ranges are inverted;
- acquisition source/retrieval metadata is malformed;
- an integrity anchor references an unknown digest;
- a verified anchor lacks verifier evidence;
- manifest or bundle digest differs from canonical content; or
- a later bundle revision omits its predecessor digest.

## 13. W3C PROV alignment

E2EESA maps:

- evidence entities → PROV Entity;
- provenance activities → PROV Activity;
- agents → PROV Agent;
- generated entities → `wasGeneratedBy`;
- used entities → `used`;
- participating agents → `wasAssociatedWith`;
- entity revisions/derivations → `wasDerivedFrom`.

The Observatory data architecture in PR 35 may materialize these relations in relational, graph and search projections without changing the canonical evidence semantics.
